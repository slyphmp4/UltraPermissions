# Налаштування UltraPermissions 5.6.9

## Один сервер

Для окремого сервера з локальним JSON-сховищем додаткових налаштувань не потрібно: міжсерверний канал вимкнено, звичайні команди та графічний редактор використовують наявну модель superadmin.

## Проксі та сервери backend

Оновіть проксі та всі сервери backend до однієї версії з виправленнями безпеки. Старий формат BungeeCord/UltraPermissions// відхиляється; змішана мережа зі старими JAR не синхронізуватиметься.

Перший запуск створює `plugins/UltraPermissions/security.properties` з новим випадковим 32-байтовим ключем і `messaging-enabled=false`. Для кластера скопіюйте **лише однакові network-key та realm** з одного довіреного вузла на решту. Задайте різні node-id, а messaging-enabled увімкніть після налаштування всіх вузлів. Не передавайте ключ через ігровий чат або повідомлення плагінів. Доступ до файла повинен мати лише власник сервера; на Windows налаштуйте відповідний ACL.

Проксі:

```properties
messaging-enabled=true
realm=ultrapermissions
node-id=proxy
proxy-id=proxy
network-key=<BASE64_KEY_32_BYTES>
```

Сервер backend, зазначений у конфігурації BungeeCord як survival:

```properties
messaging-enabled=true
realm=ultrapermissions
node-id=survival
proxy-id=proxy
network-key=<SAME_KEY>
```

Замініть `<BASE64_KEY_32_BYTES>` та `<SAME_KEY>` тим самим приватним ключем у кодуванні Base64.

На проксі node-id має збігатися з proxy-id. На backend node-id має точно відповідати внутрішньому імені ServerInfo у BungeeCord. Ідентифікатори/realm: 1–64 символи A–Z, a–z, 0–9, `_`, `.`, `-`. Спільний ключ задає спільну межу довіри всього кластера. Зміни конфігурації набувають чинності після перезапуску.

Новий канал `ultrapermissions:secure` використовує HMAC-SHA256, напрямок/відправника/одержувача/realm, часове вікно 30 секунд і одноразове значення nonce. Годинники вузлів мають бути синхронізовані. Проксі перехоплює цей канал, зокрема клієнтські та помилкові пакети. Backend не довіряє повідомленню лише через наявність Player: воно має пройти перевірку підпису. Розмір і частоту пакетів обмежено: 100 спроб перевірки за секунду загалом і 40 прийнятих повідомлень за секунду від одного відправника; черга backend — не більш ніж 256. За перевантаження повідомлення можуть відкидатися. Синхронізацію обмежено 64 одночасними завданнями, повторні сповіщення об'єднуються.

Не додавайте ключ до проєкту або JAR, що розповсюджується. Якщо ключ скомпрометовано, замініть його на всіх вузлах. Мережевий екран, закритий для прямого доступу backend і захищене пересилання залишаються частиною правильного налаштування мережі.

## Локальні облікові дані MySQL

Пароль більше не передається з backend на проксі. Налаштуйте кожен вузол окремо: наявний локальний Registry підтримується, або створіть `plugins/UltraPermissions/mysql.properties` на потрібному вузлі:

```properties
hostname=db.example.net
port=3306
database=permissions
username=ultrapermissions_node
password=<LOCAL_PASSWORD>
ssl=true
```

Замініть `<LOCAL_PASSWORD>` локальним паролем БД цього вузла. Значення hostname має відповідати імені/IP у сертифікаті. Для IPv6 використовуйте DNS-ім'я. Файл UTF-8 читається стандартним парсером Java Properties: зворотні скісні риски у значеннях потрібно екранувати. Це локальний секрет: не копіюйте файл у публічний проєкт і не надавайте доступ гравцям чи стороннім читачам резервних копій.

Якщо mysql.properties існує, він перевизначає початкові облікові дані/TLS із Registry. Зміни в GUI не оновлюють цей файл; узгодьте його вручну перед наступним запуском. Неповний/некоректний файл зупиняє запуск MySQL, а не вмикає небезпечний резервний варіант. Щоб повернутися до локального Registry, самостійно приберіть mysql.properties із каталогу конфігурації.

Для віддаленого хоста `ssl=false` відхиляється до підключення. VERIFY_IDENTITY перевіряє CA та ім'я сервера; зниження рівня захисту, отримання неперевіреного RSA-ключа, local infile і multi-queries вимкнено. Драйвер, який не оголошує підтримку VERIFY_IDENTITY, відхиляється до передавання облікових даних. Реальний JDBC-драйвер надає сервер; його немає в цьому JAR. Для власного CA налаштуйте сховище довіри JVM засобами фактичного Connector/J, а потім перевірте відмову за неправильного сертифіката/імені.

Явно задати ssl=false можна лише для точних `localhost` і `127.0.0.1`. За замовчуванням TLS увімкнено. Обмежте доступ до БД і використовуйте окремі облікові записи вузлів із мінімальними правами. Коду потрібні CREATE таблиць і CRUD у власній БД; глобальні FILE/GRANT/адміністративні права не потрібні. Наявні таблиці та дані не видаляються.

[Офіційні налаштування TLS](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-security.html).

## Оновлення, GUI та старі піктограми

У розділі «Налаштування → Персоналізація» є два незалежні перемикачі в оригінальному стилі TechsCode: сповіщення про оновлення в чаті (лише для суперадміністраторів) та автоматичне завантаження перевірених випусків із GitHub Releases. Якщо автозавантаження вимкнене, сповіщення все одно можуть повідомляти про нові версії. Вимкнення сповіщень не зупиняє автоматичне завантаження. Обидва параметри зберігаються; під час переходу зі старої версії вони спочатку успадковують попереднє значення `updaterEnabled`.

Оновлювач перевіряє стабільні опубліковані релізи та розміщує JAR у стандартній теці оновлень Bukkit. Застосування відбувається **лише під час наступного ручного перезапуску сервера**. Примусового перезапуску, мережевого loadPlugin і виконання команд restart/update через проксі немає. Локальні дії GUI потребують чинного статусу суперадміністратора.

Перед розгортанням збережіть копію робочих даних плагіна/БД. Нові піктограми отримують префікс UPI1 і формат JSON. Звичайні старі потоки Bukkit/Guava читаються з обмеженням класів, псевдонімів, глибини, посилань на об'єкти та масивів. Невідомий формат/компонент спричиняє явну помилку, а не виконання довільного класу. Дані не перетворюються зовнішнім інструментом і не стираються масово. Нестандартні старі компоненти перевірте на копії даних на тестовому сервері.

CI запускає ізольований тест Paper 26.2 / Java 25; гра з підключеним клієнтом, мережі проксі та справжнє узгодження TLS не входять до нього. Див. [сумісність](COMPATIBILITY.uk.md) та [зміни безпеки](SECURITY-CHANGES.uk.md). Вбудована телеметрія bStats налаштовується через `plugins/bStats/config.yml`; локальні конфігурації/ключі не публікуються в Git.
